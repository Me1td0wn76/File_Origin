# ADR-0006: v1 では DB を暗号化しない

- **状態**: 承認済み
- **日付**: 2026-09-21
- **関連**: D3

## 背景

File Origin の DB には入手元 URL が蓄積される。これは閲覧履歴と同等の機微情報で、保護すべきものではある。候補は平文 SQLite / SQLCipher / OS キーストア連携。

## 決定

**v1 では平文の SQLite を使い、OS のファイル権限に依存する**。暗号化は導入しない。

## 理由

- **鍵管理のコストが利得を上回る**。SQLCipher を入れるとパスフレーズの入力か OS キーストア連携が要る。常駐デーモンが起動時に DB を開く必要があるため、無人起動と暗号化は両立しにくい。ここを雑に実装すると「鍵がファイルの隣に平文で置いてある」ような、暗号化しているつもりで守れていない状態になりやすい。
- **脅威モデルに合っていない**。ローカルの攻撃者がユーザー権限でファイルを読めるなら、ブラウザの履歴 DB も Cookie も同様に読める。File Origin だけを暗号化しても全体の安全性は上がらない。
- **ディスク暗号化が正しい層**。BitLocker / LUKS / FileVault はこの問題をより確実に解く。ドキュメントでそちらを案内する方が誠実。

## 結果

- DB は `%LOCALAPPDATA%\FileOrigin\` / `$XDG_DATA_HOME/file-origin/` に、ユーザーのみアクセス可の権限で置く。
- **README にこの判断を明記する**。「ローカル完結」を謳うプロジェクトが暗号化していないことは、黙っていると期待を裏切る。何を守り、何を守らないかを書く。
- 将来 SQLCipher をオプトインで足す余地は残す（鍵は OS キーストアに置き、デーモンの無人起動を諦める構成）。
