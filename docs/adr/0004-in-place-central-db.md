# ADR-0004: in-place + 中央 SQLite（import / サイドカーを採らない）

- **状態**: 承認済み
- **日付**: 2026-09-21
- **関連**: D2、[prior-art.md](../prior-art.md)

## 背景

ファイルと入手元を結びつけて保持する方式には 3 つの流儀がある。既存 OSS の調査で実例を確認した。

| 方式 | 実例 | 仕組み |
| --- | --- | --- |
| **import** | hydrus network、Eagle、Zotero | ファイルをアプリ専用のストレージに取り込み、アプリが所有権を持つ |
| **サイドカー** | TagSpaces、gallery-dl、yt-dlp | ファイルの隣にメタデータファイルを置く |
| **in-place + 中央 DB** | （File Origin） | ファイルは動かさず、別の DB で位置と来歴を管理する |

## 決定

**in-place + 中央 SQLite** を採用する。ユーザーのフォルダ構成には一切手を触れない。

## 理由

- **import はユーザーのフォルダを支配する**。想定ユーザーは「PC を日常的に利用する人」であって、ファイル管理をアプリに明け渡す前提の人ではない。hydrus が受け入れられているのはメディアコレクションという限定された文脈があるから。
- **サイドカーはファイル数が倍になる**。移動時に一緒に動く利点はあるが、横断検索が弱く、移動追跡（本プロジェクトの中核機能）を実現できない。`~/Downloads` に `.json` が散乱する体験も悪い。
- **in-place なら段階的に導入できる**。`fo scan ~/Downloads` を試しても何も壊れない。アンインストールしてもファイルはそのまま。これは信頼を得るうえで大きい。

## 結果

- ファイルの実体は触らない。**既定では読み取りのみ**（設計方針 P6）。OS メタデータへの書き戻しはオプトイン。
- 代償として、**DB とファイルの対応が壊れうる**。ファイルが移動・削除されたときに DB が現実と乖離する。これを埋めるのが移動追跡（M3）であり、本プロジェクトで最も難しい部分になる。
- `fo export` でデータを持ち出せるようにし、DB に閉じ込めない。
