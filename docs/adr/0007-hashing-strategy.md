# ADR-0007: SHA-256 は全体を、遅延して計算する

- **状態**: 承認済み
- **日付**: 2026-09-21
- **関連**: D7

## 背景

ファイルの同一性判定に SHA-256 を使う。しかし数 GB のファイル（ゲームの Mod パック、ISO、動画）をダウンロード直後に全体ハッシュすると、記録が数十秒遅れ、ディスク I/O も食う。先頭 N MB だけの高速ハッシュで代替する案もある。

## 決定

**SHA-256 は常にファイル全体に対して計算する。ただし記録とは切り離し、デーモンが遅延して計算する。**

記録の流れ:

1. ダウンロード完了を検知したら、**即座に** `(volume_id, file_key, size, mtime)` と入手元を記録する。`sha256` は `NULL` のまま。
2. デーモンが低優先度のキューでハッシュを計算し、後から埋める。

## 理由

- **部分ハッシュは同一性判定に使えない**。先頭 N MB が同じで中身が違うファイルは普通に存在する（同じテンプレートから作られた書庫、同じヘッダを持つ動画）。同一性を誤ると入手元を取り違え、記録が信用できなくなる。File Origin の価値は記録が信用できることにあるので、ここを削ってはいけない。
- **同一性の主キーはハッシュではない**。安定識別子 `(volume_id, file_key)` が主で、SHA-256 は移動・コピー判定の補助（README §8.1 のはしごの 2〜4 段目）。だから記録時点でハッシュが無くても、追跡は始められる。
- **遅延して困る場面が少ない**。ハッシュが要るのは「別ボリュームへ移動した」「コピーか移動かを判定する」ときで、ダウンロード直後ではない。

## 結果

- `files.sha256` は `NULL` を許容する（README §10 のスキーマは既にそうなっている）。
- `sha256 IS NULL` の行は「計算待ち」。`fo verify` と GUI はこれを区別して表示する。
- **未計算のファイルが問い合わせ対象になったら、その場で計算する**（オンデマンド昇格）。待たせるが、誤った答えを返すよりよい。
- M1 で実測し、閾値（この大きさ以上は必ず遅延、以下は同期的に計算）を決める。数値はここではなく実測後に設定ファイルの既定値として置く。
